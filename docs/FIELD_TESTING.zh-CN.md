# 把 devd 放进一个真实项目

[English](FIELD_TESTING.md) · [返回 README](../README.zh-CN.md)

示例跑通只能说明示例跑通。真正值得知道的是：你原本要开两个终端、等后端、找日志，
换成 devd 以后，这件事有没有顺手一点？要是配置半天还没跑起来，那也是结果，别替工具圆场。

本文统一实际使用反馈的记录要求。工程验收仍按 [VALIDATION.md](../VALIDATION.md)
和[发布清单](../RELEASING.md)执行；不用在每个版本重新发明一套问卷。

## 先把证据说清楚

| 类型 | 能说明什么 | 不能据此声称什么 |
| --- | --- | --- |
| 工程验证：测试、示例、合成故障、固定版本对照 | 在指定版本和场景下行为符合断言 | 用户已经觉得好用、节省了时间 |
| 作者真实项目实测：维护者在自己的其它项目完成实际工作 | 该项目的接入阻力、实际结果、作者是否继续使用 | 独立开发者认可、普遍适用 |
| 独立开发者试用：非维护者在自己的项目完成实际工作 | 该使用者的反馈及已发生的重复使用 | 普遍收益或未经测量的性能优势 |

后两类用同一份记录，注明参与关系和协助程度。Agent 帮你准备配置也写进去，不能当成
“完全独立完成接入”。作者在真实项目里专门制造的故障，仍要标为人为注入；自动 smoke
仍属于工程验证。没有独立反馈就写“独立反馈未验证”，不抹掉已有作者实测，也不拿它顶替。

不设固定人数、天数、必须成功或试遍所有功能的门槛。没用到的写“未测试／不适用”，
没测过的耗时写“未知”。“愿意继续”是意愿，下一次真的使用才是重复使用事实。
同一次试用发现多个 bug，可以分开建 issue，再回链原记录，不把它算成多个使用者。

## 在你的项目里准备一次试用

选一个项目，以及你本来就需要完成的任务。记录项目当前版本、本地改动、原启动命令、
所需运行时和接入协助。确认使用预期的 devd 二进制，记录版本及完整源码 SHA 或发布
制品来源；旧发布包可能没有新源码中的命令。

试用数据库、报告和运行状态与已有数据分开。逐项核对服务命令、工作目录、应用绑定
地址和就绪探测。服务相对工作目录按配置文件所在目录解析，配置应放在相应位置。
显式声明依赖；健康接口成功只是一个观测，不能代替实际业务验证。

启动前执行 `check`、`graph`、`doctor` 和静态 `coverage`。启动、等待、状态、日志、
控制和导出使用一致的 config/profile/state，保留前台 supervisor。启动后查看
`coverage --online`，不必为了消除提示开启所有采集。

通过应用真实后端完成原本的任务。例如创建数据并刷新确认、做一处实际修改、查看
聚合日志，或重启服务后重新等待就绪。应用已有故障及其绕行方式与 devd 行为分别记录；
mock 或 Demo 模式不能验证后端接入。

只有真实工作需要时，再扩展任务门控、事故记录、Agent/MCP 或恢复配方。这些能力仍
分别显式开启，首次试用不用覆盖全部功能。失败、未测试和未知照实保留，不凑成功清单。

结束后正常停止，等 supervisor 退出。分享前检查报告，再清理仅属于本次试用的配置、
数据和产物，保留已有文件、依赖与本地改动。各命令的限制和行为见
[命令指南](COMMANDS.zh-CN.md)。

## 试完只交这一份

可以直接把下面内容回复给维护者，或使用英文的
[Field feedback issue 模板](../.github/ISSUE_TEMPLATE/field-feedback.yml)。项目可匿名；
不要求公开私有仓库、token、环境变量正文或完整日志。若反馈涉及漏洞，按
[安全政策](../SECURITY.md)单独报告。

```text
日期与关系：作者真实项目实测 / 独立开发者试用；谁协助了接入？
环境：devd 版本、完整 SHA/发布制品来源、本地改动、系统/架构；项目版本与技术栈。
原来的工作：原启动命令、这次真正想完成什么。
实际过程：做了哪些步骤、用了哪些能力；哪些未测试/不适用；耗时未测就写未知。
卡点：原始错误、失败步骤、绕行和放弃原因；没有则写无。
结果与证据：完成/部分完成/阻塞/放弃；报告或 issue 链接；真实事故/人为注入/无事故。
接下来：继续/暂缓/放弃/未决定及原因；以后真用第二次，再补日期和具体任务。
```

拿到实际试用记录再更新 [Value evidence](../VALIDATION.md#value-evidence)。
Agent 执行的集成检查仍属于工程证据；准备去试不能提前写成已经完成人类真实试用。
